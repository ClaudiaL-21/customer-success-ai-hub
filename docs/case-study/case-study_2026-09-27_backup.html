The problem

CSMs have plenty of data and too little direction

A CSM with 30+ accounts has usage data, tickets, emails, NPS and renewal dates spread across tools. The hard part is deciding on Monday morning which three customers to call and what to say. Generic AI summaries make this worse when they invent facts or suggest an upsell to an account that is about to churn.

I wanted a tool that ranks accounts with transparent rules, uses AI only where it adds judgement, and never lets an AI suggestion reach a customer without a human decision.

Architecture

The Hub decides what is true. n8n does the work.

Scores and rankings are calculated in the Hub. n8n handles the two things that touch the outside world: calling an AI model, and executing an action a CSM has approved.

One contract for six AI modes

Portfolio summary, portfolio questions, account insight, account questions, team prioritisation and QBR drafts all use the same webhook. The Hub sends a system prompt, a user prompt and a token budget. n8n returns one field.

// Hub → n8n
{ "system": "...", "user": "...", "maxTokens": 3800 }

// n8n → Hub
{ "text": "<model output as JSON>" }

Switching the model or provider is a change inside n8n. The Hub doesn't need a release for it.

Built to fail safely

  • Every call carries a shared-secret header, x-cs-ai-hub-secret. Without the secret configured, the Hub makes no call at all.
  • Each workflow has its own bounded timeout, so a hanging model call can't block the CSM.
  • A response that breaks the contract is rejected, not "repaired".
  • Error bodies from n8n are never shown or logged, only the status.
  • A failed send is never retried automatically. The CSM's edits are kept and they decide.

Program design

The CS decisions behind the software

Most of the work was deciding what the AI may and may not do. These rules are enforced in code, not only asked for in a prompt.

The ranking is never the model's

Which accounts come first is a fixed formula of risk, ARR, renewal date and engagement. The AI only explains the ranking and suggests actions.

One action, not a to-do list

CSMs already have too many half-prioritised lists. The copilot must pick the single most important action and say why it beats the alternatives.

No upsell to a churning customer hard rule

If a high-risk account gets a growth suggestion, the server replaces it with a risk-mitigation action built only from known facts.

Recommend is not commit

A timeframe the AI proposes is phrased as a proposal. Only commitments already documented in the account history may read as agreed.

Internal language stays internal QBR

Health scores, risk labels and CSM notes can't flow into the customer version of a QBR. Sensitive sections are blanked on the server, whatever the model returns.

Confidence means evidence transparent

Each insight shows how strong the underlying evidence is: how many sources, how recent, how varied. It never claims how likely the AI is to be right.

Planned next · not built yet

From static data to live customer signals

The demo portfolio is still a fixed dataset. The next sprint connects the Hub to incoming customer emails and tickets through n8n:

  • Signal intake: an AI step extracts account, sentiment, topic, urgency and feature requests from each message.
  • Risk escalation: when a signal pushes an account over a threshold, the CSM gets a Slack message with a suggested action and approves it there.
  • Weekly voice-of-customer digest: top feature requests by ARR, sent to product every Monday.
  • Error workflow: any failed node alerts the owner immediately.

All accounts, people and customer messages are fictional demo data. No real customer data is stored or sent.
